---
name: build
description: Use when the operator says "build X 3", "build 004", "ship 004", "start X 3", "do what's accepted in X" or "build what's accepted in X" - X a repo in the bmesh registry, the number a spec id - or "hold X", "hold land on X", "build these, land none until I say", "release X", "stop X" or "wipe X" about a lead or spec being built. Dispatches the accepted spec with bmesh build, watches the lead with bmesh watch, relays its asks, holds and releases leads with bmesh hold and unhold, stops them with bmesh node stop, wipes them with bmesh node forget --wipe, reports the thread and drains its leads' feedback into fixes and proposed specs.
---

# Build

`bmesh build` does the checking (a ship row, a spec that reads `accepted`, no other build family of the repo still running or holding feedback, a green `main`, a free node path, the host's lead cap) and records `building` on `main` before the lead starts; relay its refusal rather than redo it.

1. **Where it runs.** `bmesh repos show <repo> --json` gives the row; `host` is where the lead runs. On this box run the command here; on another box run it as `ssh -o BatchMode=yes <host> "bash -lc '<command>'"` (ssh joins its arguments into one remote command line, so the inner command is quoted twice). When that host can't be reached from here, say so and stop.
2. **The command.** One spec: `bmesh build <repo> <NNN> [--model <m>]` (a rebuild of a path whose node is still live: `--path <repo>-<NNN>-2`, as the refusal says). Everything accepted: `bmesh build --accepted <repo> [--model <m>]`, which prints `started`, `waits` or `not started` per spec. The JSON line carries the lead's `path`, `thread`, `branch`, `worktree`, `model`, the `building` commit and its build `family`; `--accepted` names the family in each `started` line and a closing `family <F>` line. A spec that defines a command `main` or another spec already has carries the warning `choose-ideas` printed at its accept: `warnings` in the JSON line, `; warning: ...` at the end of its `started` line. What you dispatch together is one family: pass the first command's family as `--family <F>` to every later `build` of the batch, on this repo or another (over ssh it goes on the remote command line), so step 7 reads one queue.
   - **Specs that edit the same files** go one after another, not together: leads building the same files at once make the later one pay at land for the rebase conflicts. Read each accepted spec's Proposal before dispatching. When two name the same files, `--accepted` would start both, so build the batch one spec at a time, each with `--family <F>`, and make its two checks yourself: hold back a spec whose body names a lower id that isn't `done`, and start none while three leads of the repo are live. Hold back the later spec of an overlapping pair too, and build it once the first reads `done`. When the first ends `blocked` or `silent`, don't build it: report it as waiting on that spec (step 6). Drain the family (step 7) at the `watch-done` of the last lead you start.
   - **Held** is not a failure. `held: <family> is still running (...); watch it with bmesh watch --nodes <paths>` or `held: <family> has N feedback pending` (`--accepted`: one `held <family>: <why>` line, nothing started) means the repo's last build run isn't finished. Tell the operator what holds the build. When the family is one you dispatched, arm `bmesh watch` on the named nodes (step 4); at `watch-done` drain it (step 7), then run the same `build` again. A family another coordinator owns you report to the operator, who decides whether to wait or to pass `--force`; never pass `--force` on your own.
   - **Main is red**: `main is red at <sha8> <subject>: verify fail t:<tree8>` and the tail of the verify's output. Report it to the operator with the failing test it names; never retry it. Only the spec that fixes it is dispatched past it, with `--force`, when the operator says so.
3. **The Fable fallback.** A lead runs on its spec's judge at `[models] lead_effort` (`high` by default); this applies only to a Fable model (a `fable` judge, or the operator's `--model`). When the runner rejects it (an error naming the model, consent or credits; the spec is back to `accepted`, `Dispatch NNN: did not start`), run that one spec once more as `bmesh build <repo> <NNN> --model claude-opus-5-5` and tell the operator what the runner said. After `--accepted`, only the rejected specs are rerun, one by one, each with `--family <F>` of the batch (in a new family the batch's running leads would hold it): a `--model` on `--accepted` would override every other spec's judge. Any other failure is reported as printed, never retried.
4. **Watch the leads.** `bmesh watch --nodes <path>[,<path>...] --timeout 30m` prints one line per event (`<at> <path> <event> <text>`) and `watch-done` once every node is `done`, `blocked` or `silent`; exit 5 is the timeout, re-arm it with `--since <the last line's time>`. Where the harness has a Monitor, arm it on the watch and let it wake you; otherwise run the watch in the background and read its output when it exits. Never poll the runner (T3, tmux, the session files) in a loop.
5. **Relay asks.** An `ask` line is a question only the operator can answer: put it to the operator in their words, and send the answer back with `bmesh --node operator send <path> "<answer>"`. A `blocked` line is reported with its reason; `done` with its commit.
   - **A row change.** A lead that asks for a registry row's `verify` or `setup` to be published needs no scaffold step after it: within a minute of the publish the row's host box commits the files on `main` and pushes `<host>: scaffolded <repo> for registry v<N> ...`; tell the lead to rebase onto `origin/main`. Only a `scaffold <repo> ... failed` or `has no checkout` push asks for `bmesh scaffold <repo>` by hand (the `scaffold` skill).
   - **Holds.** To stop a lead until you or the operator say so (land in order, wait for something else to land first, a diff the operator wants to read, low quota, a redirect), hold it; never send a free-text "hold" and a release phrase. `bmesh --node operator hold <path> --text "<why>"` holds it before land (it keeps building; `land` refuses), `--gate now` stops it at its next inbox, `--family <F>` holds every live lead of a family, and dispatching with `bmesh build ... --hold land` writes the hold before the lead starts ("build these, land none until I say"). The operator says "hold X" (`--gate now`), "hold land on X" (the default gate) or "release X", X a lead's path or spec. A `held` line in the watch is the lead at its gate: relay it as one line (`<path> held before land: <why>`), never as an ask. Release with `bmesh --node operator unhold <path>|--family <F> [--text "<words>"]`, which wakes it; `<path>: not held` needs nothing. A lead that has run `bmesh ready` (state `landing`, its box's daemon landing its change) isn't woken by a hold or its release: its daemon runs `held` for it, and the release resumes the daemon's landing. Its `landing` state is calm, never an ask: relay it as one line only when asked. `bmesh release <repo>` is the release tag (step 7), not this.
   - **Stops.** When the operator says "stop X" (X a lead's path or spec), the lead is to end, not pause: `bmesh --node operator node stop <path> --text "<why>"`, run on any box: another box's thread is stopped there when that box accepts `stop-thread`; when it refuses, run the same command on that box (step 1). It stops the lead's executors and then its thread, writes it `blocked` with `stopped by operator: <why>` and prints a line per node; the daemon never wakes it again. Never send a free-text STOP message: a message is mail, and mail wakes a lead. To resume a stopped lead, `bmesh --node operator send <path> "<what to do>"`, the one thing that wakes it. A thread the operator interrupted in T3 reads `blocked: stopped in t3 by the operator` within a minute and stays that way: relay it as stopped, not as a block to solve. A stopped lead is cleared with `bmesh node forget <path>`. When the operator says "wipe X" (or to wipe it "as if it never ran"): `bmesh --node operator node stop <path> --text "<why>"`, then `bmesh node forget <path> --wipe` (`--dry-run` first shows what goes), which removes it and every node under it from the mesh, its brief, worktree and branch; never the `nats` CLI or the mesh token.
6. **Report** the started threads (path, thread id, host, model, family; say if it fell back to Opus), each one's warnings as printed (a command another spec or `main` already has: the operator's to rename, or to read past when the spec changes that command on purpose), and what was left waiting and why (`--accepted`'s `waits` lines, and a spec held back behind one it shares files with or depends on).
7. **Drain the feedback.** Once `watch` prints `watch-done` for a family's leads, `bmesh feedback list <family>` prints what its leads left, one issue per line, each starting with its stream sequence.
   - **bmesh's own repo** (the repo whose `go.mod` declares bmesh's module) isn't yours to triage: the daemon starts its fixer when an issue names it. Report the fixer on `bmesh mesh-status`'s `fixes: N pending for <repo> (<fixer> working)` line as `fixer <path> has them` (`starts within a minute`: the daemon is about to start it; `blocked` or `done; they wait on you`: relay that line to the operator). The fixer rules on those issues, builds and releases that repo; leave them pending, since it drains them.
   - For every other issue, synthesize. Merge duplicates. Drop an issue a spec on the repo's `main` already covers, whatever its status (`bmesh spec list --repo <repo>`, then read the likely ones), so a rejected idea doesn't come back; drop one a `fixed` commit settled, unless the general case is left, and one a quick fix on `main` already names (`git -C <repo path> log origin/main --oneline -E --grep '^Quick fix from .*#<seq>([^0-9]|$)'`: a quick fix whose drain never ran).
   - **Quick fix**: one cause, one obvious change, XS or S. Make it yourself, here, as the `quickfix` skill's **Where**, **Make it**, **Verify**, **Review** and **Land** steps make a change: no spec and no lead. Its commit is titled `Quick fix from <family> #<seq>: <what it changes>` (several issues: `#<seq>, #<seq>`), which is its record on `main`. There is no operator review.
   - **Needs thought**: everything else. Write its spec yourself, here, as the `ideate` skill writes one idea the operator brought: `ideate-engineer` sections 1 to 4 for that one issue (read the repo and its ledger, measure, widen and attack it, write the half-pager), its id claimed with `bmesh spec next-id --repo <repo>` and then landed, the body from `bmesh spec template --repo <repo>`, `status: proposed`, `proposed_by` your own thread, `from_feedback: <family> (<the leads that hit it>) #<seq>`. Land each as `Feedback NNN: proposed from <family>` and push; it waits on the operator's review (`buildermesh:choose-ideas`), never built from here. Never run `bmesh ideate` for feedback: the issues are already the ideas, and a round starts two threads that propose ideas of their own around them.
   - Once every issue you triaged has gone to a pushed quick fix or a landed spec, `bmesh feedback drain --seq <their sequences, comma-separated>`, which deletes exactly those; the quick fixes' titles and the specs' `from_feedback` are the only record left. If you stop between list and drain, the family stays pending and `bmesh mesh-status` shows `feedback: N pending in <family>`.
   - Report one line per issue: `<issue>: fixed by <sha8>`, `proposed NNN`, `already NNN`, `dropped: <why>` or `to the fixer`, then `drained N`.
   - **Release.** Last, run `bmesh release <repo>` for each repo a lead of the family or one of your quick fixes landed in that already has a release tag (`git -C <repo path> tag --list 'v*'` prints one), except bmesh's own repo while a fixer is live (a `<repo>-fix-<N>` node in `bmesh mesh-status` neither `done` nor `blocked`), which releases it once its queue is empty: the batch is done, so it gets its version once. In bmesh's own repo (the repo whose `go.mod` declares bmesh's module), level ponytail first when `scripts/ponytail.sh check` says a newer release of it is out: `scripts/ponytail.sh level`, read the diff (the copies become agents' instructions), commit it to `main` as `Level ponytail to vX.Y.Z`, verify, push, and name the release in your report. Then write its upgrade notes: `bmesh release <repo> --dry-run` names the tag and the specs landed since the last one (while specs with steps have no notes yet it refuses, naming those specs and the file to write); read the `## Upgrading` section of every spec landed since the last tag and distil them into the fewest true steps (a key one spec adds and another drops never appears; two moves of the same file become one; an ask whose default keeps today's behaviour stays an ask), written for any fleet; write them to `docs/upgrading/vX.Y.Z.toml` in the format the Upgrade notes section of bmesh's manual (`docs/manual.md`) documents, commit it to `main` as `Upgrade notes vX.Y.Z` and push, then release. You have the final say over what goes in; the spec sections are your input, not the notes. When every section is empty or reads `nothing`, there is no file to write. `release` refuses (exit 3) when steps have no notes, or when the notes don't parse or name a key the binary doesn't know: fix the file and release again. It prints `released <repo> vX.Y.Z at <sha8> (NNN, ...)`; report that line. `nothing to release since ...` (nothing under code landed) and `already released ...` need nothing; a `held` or `main is red` refusal is reported to the operator with its line, never passed by hand. A repo with no release tag is not released from here: its first tag is the operator's (or a lead's, by hand).

End with one line: what is started (or landed, when the watch saw `done`), the release cut (`released <repo> vX.Y.Z`), and what waits on the operator: an unanswered ask, a block, the specs with steps for the operator still open (`bmesh spec steps --repo <repo>` prints a line per spec; name each and the command that lists and ticks its steps, `bmesh spec steps NNN --repo <repo>`, never the steps themselves, so the list lives on the mesh rather than in the chat), or nothing but the push. Every quick fix you made and every spec you proposed from feedback is named in it, the proposed ones as waiting on the operator's review. Say what each thing in it is in plain words (a spec or issue by what it does, its number after it in brackets if at all): the line is final and reads on its own, with nothing the operator has to look up.

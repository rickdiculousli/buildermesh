# Build

`bmesh build` does the checking (a ship row, a spec that reads `accepted`, no other build family of the repo still running or holding feedback, a green `main`, a free node path, the host's lead cap) and records `building` on `main` before the lead starts; relay its refusal rather than redo it.

1. **Where it runs.** `bmesh repos show <repo> --json` gives the row; `host` is where the lead runs. On this box run the command here; on another box run it as `ssh -o BatchMode=yes <host> "bash -lc '<command>'"` (ssh joins its arguments into one remote command line, so the inner command is quoted twice). When that host can't be reached from here, say so and stop.
2. **The command.** One spec: `bmesh build <repo> <NNN> [--model <m>]` (a rebuild of a path whose node is still live: `--path <repo>-<NNN>-2`, as the refusal says). Everything accepted: `bmesh build --accepted <repo> [--model <m>]`, which prints `started`, `waits` or `not started` per spec. The JSON line carries the lead's `path`, `thread`, `branch`, `worktree`, `model`, the `building` commit and its build `family`; `--accepted` names the family in each `started` line and a closing `family <F>` line. What you dispatch together is one family: pass the first command's family as `--family <F>` to every later `build` of the batch, on this repo or another (over ssh it goes on the remote command line), so step 7 reads one queue.
   - **Held** is not a failure. `held: <family> is still running (...); watch it with bmesh watch --nodes <paths>` or `held: <family> has N feedback pending` (`--accepted`: one `held <family>: <why>` line, nothing started) means the repo's last build run isn't finished. Tell the operator what holds the build. When the family is one you dispatched, arm `bmesh watch` on the named nodes (step 4); at `watch-done` drain it (step 7), then run the same `build` again. A family another coordinator owns you report to the operator, who decides whether to wait or to pass `--force`; never pass `--force` on your own.
   - **Main is red**: `main is red at <sha8> <subject>: verify fail t:<tree8>` and the tail of the verify's output. Report it to the operator with the failing test it names; never retry it. Only the spec that fixes it is dispatched past it, with `--force`, when the operator says so.
3. **The Fable fallback.** A lead runs on its spec's judge at `[models] lead_effort` (`high` by default); this applies only to a Fable model (a `fable` judge, or the operator's `--model`). When the runner rejects it (an error naming the model, consent or credits; the spec is back to `accepted`, `Dispatch NNN: did not start`), run that one spec once more as `bmesh build <repo> <NNN> --model claude-opus-5-5` and tell the operator what the runner said. After `--accepted`, only the rejected specs are rerun, one by one: a `--model` on `--accepted` would override every other spec's judge. Any other failure is reported as printed, never retried.
4. **Watch the leads.** `bmesh watch --nodes <path>[,<path>...] --timeout 30m` prints one line per event (`<at> <path> <event> <text>`) and `watch-done` once every node is `done`, `blocked` or `silent`; exit 5 is the timeout, re-arm it with `--since <the last line's time>`. Where the harness has a Monitor, arm it on the watch and let it wake you; otherwise run the watch in the background and read its output when it exits. Never poll the runner (T3, tmux, the session files) in a loop.
5. **Relay asks.** An `ask` line is a question only the operator can answer: put it to the operator in their words, and send the answer back with `bmesh --node operator send <path> "<answer>"`. A `blocked` line is reported with its reason; `done` with its commit.
6. **Report** the started threads (path, thread id, host, model, family; say if it fell back to Opus), and what `--accepted` left waiting.
7. **Drain the feedback.** Once `watch` prints `watch-done` for a family's leads, `bmesh feedback list <family>` prints what its leads left, one issue per line, each starting with its stream sequence. Then synthesize:
   - Merge duplicates. Drop an issue a spec on the repo's `main` already covers, whatever its status (`bmesh spec list --repo <repo>`, then read the likely ones), so a rejected idea doesn't come back; drop one a `fixed` commit settled, unless the general case is left.
   - **Quick fix**: one cause, one obvious change, XS or S. Write the spec yourself: the id from `bmesh spec next-id --repo <repo>`, the body from `bmesh spec template --repo <repo>`, `status: accepted`, `proposed_by` your own thread, `from_feedback: <family> (<the leads that hit it>)`. Land it on the repo's `main` as `Feedback NNN: accepted from <family>` and push, then run `bmesh build <repo> NNN` straight away, with no operator review; that mints a new family, and you watch its lead the same way, this step included.
   - **Needs thought**: everything else. Write its spec yourself, here, as the `ideate` skill writes one idea the operator brought: `ideate-engineer` sections 1 to 4 for that one issue (read the repo and its ledger, measure, widen and attack it, write the half-pager), the same id and template as a quick fix, `status: proposed`, `proposed_by` your own thread, `from_feedback` as above. Land each as `Feedback NNN: proposed from <family>` and push; it waits on the operator's review (`buildermesh:choose-ideas`), never built from here. Never run `bmesh ideate` for feedback: the issues are already the ideas, and a round starts two threads that propose ideas of their own around them.
   - **The loop bound**: an issue left by a lead whose own spec carries `from_feedback` is never a quick fix; it is always written up as `proposed`.
   - Once every issue has gone to a spec, `bmesh feedback drain <family> --through <the last sequence you listed>`; a message that arrived after your list stays for the next pass. The specs' `from_feedback` is the only record left. If you stop between list and drain, the family stays pending and `bmesh mesh-status` shows `feedback: N pending in <family>`.
   - Report one line per issue: `<issue>: fixed by NNN (started)`, `proposed NNN`, `already NNN` or `dropped: <why>`, then `drained N from <family>`.

End with one line: what is started (or landed, when the watch saw `done`), and what waits on the operator: an unanswered ask, a block, or nothing but the push. Every spec you accepted or proposed from feedback is named in it, the proposed ones as waiting on the operator's review. Say what each thing in it is in plain words (a spec or issue by what it does, its number after it in brackets if at all): the line is final and reads on its own, with nothing the operator has to look up.

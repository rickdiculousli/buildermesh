# Work

Start from the operator's problem, never from a routing word. Read it and the code, size the work, and take the first rung below that holds. Never ask which path to take, and never make the operator restate their state (testing, low on budget, away) once said: keep it for the session and name it on the first line of each reply while it holds ("Holding for your QA: ..."). The binary does the checking (the row, holds, a red `main`, a free path, the lead cap) and refuses with what to do next: act on its refusal, never redo its checks, and pass `--force` only when the operator says so. Only the operator, in this chat, starts a round or a lead: a subagent or reviewer you start never runs `bmesh ideate`, `build`, `lead start` or anything else that starts a thread.

**Read first.**

- **The repo**: the one named, else the one this session runs in. `bmesh repos show <repo> --json` has its path, `host` and verify.
- **What's in flight**: `bmesh mesh-status` (leads, rounds, asks, landings); for an idea or a pick, `bmesh spec list --repo <repo>` too. A spec being built reads its old status in the ledger until it lands `done`: only its lead's node says it is building or blocked. On a box with no hub (`no hub at <addr>: is bmesh serve running?`) nothing is in flight; rungs 1 to 4 work without one, and leads and rounds need `bmesh serve`.
- **The code** the problem touches, before deciding anything.

## The ladder: stop at the first rung that holds

1. **A question, or they're testing.** Answer from the code and change nothing. While they QA or say to hold ("hold off", "don't fix yet"), leave what they're testing alone (no edit, restart, rebuild or deploy of it) and start nothing. Keep a numbered list, each item with what they saw, its cause (or `not looked at`), the fix and its size, and answer each in one line: `3 noted: <cause>; fix: <change> (XS)`. A "fix X" goes on the list as picked unless they say now. Their release ("go", "fix 1 and 3") makes the picked items as one change by rung 3, a commit each, with one verify, one review sized by the batch and one push; what wasn't picked stays listed.
2. **Already done or being built.** Say which, with the lead's path and state or the commit on `main`, and stop. Words for a lead in flight go to it: `bmesh --node operator send <path> "<their words>"`.
3. **This session can make it: XS, S or M** (XS one file, S one module, M crosses modules). A problem reported is a change to make. No spec, spec id, lead or commit that only records state:
   1. **Where.** A worktree of your own on a branch from `origin/main` (`git -C <repo path> worktree add <dir> -b <branch> origin/main`, `<dir>` the harness's or under `~/.bmesh/worktrees/<repo>/`), never the repo's checkout. A repo with no checkout on this box is made on its row's `host`.
   2. **Make it**: the smallest change that does what was asked, by the repo's `AGENTS.md`, with the docs it keeps exact changed in the same commit. Run the tests it touches as you go.
   3. **Verify.** Commit, then `bmesh routine run verify` in the worktree until it ends `verify ok`. A repo with no `verify` kind: run its verify commands yourself.
   4. **Review** your diff (`git diff origin/main...HEAD`) by the `ponytail-review` skill, here, at your own effort. Fix its Must fix and Should fix findings once and verify again; the rest go in your report. For M, one more review: Opus at medium effort in a fresh session (a subagent), given the operator's words, the diff and the verify line, told to review by `ponytail-review` and to start nothing.
   5. **Land.** `git fetch origin`, rebase onto `origin/main` (verify again when it brought commits), `git push origin HEAD:main`; when refused because `main` moved, fetch, rebase, verify and push again. Bring the repo's checkout level when it is on `main` and clean (`git -C <repo path> merge --ff-only origin/main`), then remove your worktree and branch. Never move, reset or push commits on `main` that aren't yours.
   6. **Release** only when they want it running now and the repo is released by tag (`git tag --list 'v*'`): see Releases.
4. **It needs their eyes first**: L (it changes an interface others depend on), a call of taste, a release or deploy they didn't ask for, or a spend past the budget they set. Write the plan in five lines: what changes, where, how it is checked, its size, and what you won't do; end on the one question their ok answers. When a grilling skill is installed here (one named like `grill-me`), offer it in one line. Start it on their ok, here by rung 3 with the review at high effort, or by rung 5 when it is long or splits, with the plan as the spec. A change that grows to L while you make it stops there with the same five lines.
5. **Leads**, for specs they pick, pieces that run independently, or work longer than this session should carry. `bmesh build <repo> <NNN> [<NNN>...] [--context -]` starts a lead per spec, three at a time per repo, and prints a line per spec: `started`, `building` (a live lead has it), `waits` (on a lower spec it names, or for a slot) or `not started` with the refusal (one spec prints its lead as a JSON line, or refuses). Their words beyond the pick ("2 smaller", "keep the old flag") go in `--context`, on stdin through a quoted heredoc. A model named for one spec ("3 on opus") is that spec's own `bmesh build <repo> <NNN> --model <m> --family <F>`, run apart, since `--model` on a batch overrides every spec's judge. Report each `warning:` build prints as printed (a command another spec or `main` already defines): renaming one is the operator's call. Specs that edit the same files go one after another. What starts together is one family: pass the first build's `--family <F>` to the later ones. A spec written from the chat for a lead lands first (`bmesh spec next-id --repo <repo>`, `bmesh spec template`, `status: proposed`, committed as `Propose NNN: <title>` and pushed). Write each lead's brief as what can be checked (outputs, refusals, tests), and name the spec or brief file in your reply before the leads start, so the operator can read it while it's cheap to change. From then on carry only the specs, the leads in flight and what to check when each reports: the rest of how you got there is the leads' to read again, not yours to keep. Then watch, relay and drain, as below.
6. **What to do next** ("what would you improve in X", "ideas for X"): `bmesh ideate <repo>`, a round of two threads that returns a ranked pitch: watch it, and when it settles, give the pitch as its line carries it; one idea of theirs to be specced at length in a thread: `bmesh ideate <repo> --idea --context -`. Their answer starts the work: "1 and 3" builds those (rung 5; an XS or S line the pitch carries without a spec is made by rung 3), "2 no, <why>" declines it (`bmesh spec set --repo <repo> --id NNN --status rejected --field reason="<why>" --land`), "4 later" sets `later` the same way. A spec a live lead is building is declined only once the operator has said to stop that lead (`node stop`, below), since its land would bring `done` back. Map positions to the pitch they answered, the newest one they saw; when a number could mean two things, ask in one line.

**Never cut**: what the operator is running is never touched; verify; a review sized to the risk; the push state, from a fresh fetch; their say over releases, deploys and big spends.

## Running leads and rounds

- **Where a command runs.** A lead or round runs on its row's `host`. On another box, run the command there: `ssh -o BatchMode=yes <host> "bash -lc '<command>'"` (quoted twice, since ssh joins its arguments), with the operator's words on stdin. A host you can't reach is said and nothing starts.
- **Watch.** `bmesh watch --nodes <paths> --timeout 30m` prints one line per event and `watch-done` when every node is done, blocked or silent; on exit 5, re-arm it with `--since <the last line's time>`. Arm it under a Monitor where the harness has one, else in the background. Never poll the runner.
- **Relay.** An `ask` goes to the operator in their words, and the answer back with `bmesh --node operator send <path> "<answer>"`. A `blocked` is reported with its reason, a `done` with its commit; a `held` or `landing` line is calm, one line when asked.
- **Hold, release, stop, wipe.** "Hold X": `bmesh --node operator hold <path> --gate now --text "<why>"`; "hold land on X" or "build these, land none until I say": the default gate, or `bmesh build ... --hold land`; "release X" when X is a held lead: `bmesh --node operator unhold <path>`. "Stop X": `bmesh --node operator node stop <path> --text "<why>"`, which ends it for good (a message resumes it); never a free-text stop, since mail wakes a thread. "Wipe X": stop it, then `bmesh node forget <path> --wipe` (`--dry-run` first).
- **The Fable fallback.** When the runner rejects a Fable model (its error names the model, consent or credits), run that one spec or round again with `--model claude-opus-5-5` and say what the runner said. Any other failure is reported as printed.
- **Feedback.** At `watch-done` for a family, `bmesh feedback list <family>`. Feedback naming bmesh's own repo is its fixer's: leave it pending. For the rest, merge duplicates and drop what `main` already covers (a spec, or a commit naming its `#<seq>`). Make each one-cause XS or S issue by rung 3, titled `Quick fix from <family> #<seq>: <what it changes>`. Write each other one as a proposed spec, `from_feedback: <family> (<the leads>) #<seq>`, landed as `Feedback NNN: proposed from <family>`, for the operator to pick. Then `bmesh feedback drain --seq <those sequences>`.
- **Releases.** "Ship X", "cut a release of X", or "release X" when X is a repo and no lead of it is held, is `bmesh release <repo>` now, by the steps below: they asked for it. A batch of leads ends with `bmesh release <repo>` for each repo it landed in that is released by tag, once all its leads are done (bmesh's own repo waits while its fixer is live). In bmesh's own repo, first level ponytail when `scripts/ponytail.sh check` says a newer release is out (`scripts/ponytail.sh level`, read the diff, commit `Level ponytail to vX.Y.Z`, verify, push). Then write the upgrade notes: `bmesh release <repo> --dry-run` names the specs since the last tag; distil their `## Upgrading` sections into the fewest true steps in `docs/upgrading/vX.Y.Z.toml`, as the manual's Upgrade notes section documents, commit `Upgrade notes vX.Y.Z`, push, then release. A `held` or `main is red` refusal is reported, never forced.
- **Status.** For "what's building" or "what's waiting on me": `bmesh mesh-status`, summarised one line per lead or round, asks first, then blocked, silent, held, landing and what landed since the last look; a quiet mesh is one line. A box's hold (`<box>: <repo> waits for your approval`) waits on the operator too: say what it holds and the `bmesh hosts approve <id>` they run in a terminal on that box; the session never runs it itself. Then the landed specs with steps for the operator still open (`bmesh spec steps`), each with the command that ticks them. `bmesh update --notice` lines go last, word for word.

## Long sessions

- **A state file** for each stream of work you carry (a batch of leads, a run of changes), somewhere that outlives this session, named in your replies. At each milestone (a landing, a settled round, a batch started) update it: what landed, what's in flight with its ids, what's next, the decisions and the lessons.
- **The line.** Once your context crosses a nudge, a `bmesh` command ends with `bmesh: this session's context is <N>k. <advice>`. Act on its advice at your next milestone, never in the middle of something and never while exploring or investigating. Right before executing a finished design is a milestone: run `bmesh context` there.
- **To compact**, update the state file first. Where the harness lets a session queue `/compact <what to keep>` into its own thread (T3 Code's `t3_thread_send` with mode `queue`), queue it, then a message that resumes the work from the state file, unless the operator paused you. Elsewhere, ask the operator to type `/compact`. Say it in one line of the reply.
- A subagent's `bmesh` commands read its parent's context: the line is the parent's to act on.

End with one line: what changed or started (the commit on `main`, or the lead or round and its host), its push state from a fresh fetch, what you didn't check, and what waits on the operator, each named in plain words. The line is final and reads on its own.

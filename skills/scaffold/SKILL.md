# Scaffold

`bmesh scaffold` gives a ship repo what a build expects of it from its registry row and the binary (the three marked `AGENTS.md` sections, the engineering rules block, `docs/proposals/README.md`, the routine kinds the row names) and nothing else. It runs from this box against the repo's checkout (`path` in `bmesh repos show <repo>`).

A published change to the row's `verify` or `setup` needs no scaffold here: the row's host box commits the verify kind and `[setup]` on `main` itself and pushes `<host>: scaffolded <repo> for registry v<N> ...`. This skill is for what that leaves: a repo's first scaffold, its rules, `AGENTS.md`'s done block (which that push names when it is stale), a host box with no checkout or an older bmesh, and a rescaffold whose push says it failed.

1. **Show the diff.** `bmesh scaffold <repo> --check` prints the unified diff and exits 1 when there is one; exit 0 with no output means the repo is scaffolded: stop here and say so, unless the operator asked to change its rules (step 2). An exit with a `bmesh:` line on stderr and no diff is an error, not a diff (a row that is not `ship`, a path without a row, a kind in the row's `routines` with no example to seed from, which names the `.bmesh/routines/<kind>.toml` to write by hand, a rules marker naming a set bmesh doesn't ship): report it as printed and stop. Otherwise show the operator the diff (the whole thing when short, else the files and a line per section). A first line `AGENTS.md: rules are customized; kept as written` means the repo's rules block was edited and is kept.
2. **The rules interview**, before anything is written, when the repo's `AGENTS.md` has no `<!-- bmesh:rules` block (its first scaffold, or its first since bmesh shipped rule sets) or the operator asked to change its rules ("change X's rules"):
   - Show each set's lines, from the Rule sets section of bmesh's manual (`docs/manual.md`), and ask which to pick: several, one or none. Recommend `core`, plus `tests` when the repo has tests and `design` when it holds stateful or concurrent code, each with the one clause of evidence you saw ("`tests`: it has 40 `_test.go` files").
   - Write the pick as an empty block at the end of `AGENTS.md`, `<!-- bmesh:rules <sets> -->` and on the next line `<!-- /bmesh:rules -->` (`<!-- bmesh:rules -->` for none), or rewrite the existing opening marker to that; step 3's `bmesh scaffold` fills it. Put no text of your own in the block now: a marker with set names and no hash is a fresh pick, and scaffold replaces whatever is under it.
   - On a block whose marker reads `customized`, say so and ask whether to keep it as written or go back to bmesh's sets (the set names back on the marker); keep it unless the operator says otherwise.
   - Say the text can be edited afterwards: scaffold keeps an edited block and marks it `customized`.
3. **Write it.** `bmesh scaffold <repo>`, which prints `wrote <file>` per file. The one line it may add on stderr says the row lists no verify commands, so no `verify` kind was written; pass it on, it is a fact about the row, not a failure. With no pick asked for, the binary gives a repo with no rules block `core`.
4. **Clear conflicts out of the repo's own prose**, after an interview, now that the block holds the picked rules. Read the repo's instruction text outside bmesh's markers (`AGENTS.md`, `CLAUDE.md`, and any file `AGENTS.md` says to read at the start) for lines that restate a picked rule or contradict one, and show each beside the rule line it meets. A restatement is deleted, since the block now carries it. A contradiction asks which wins: keep the repo's line and cut or reword the rule in the block (which marks it customized), or delete the repo's line. Flag too each line that rests on a set the operator didn't pick (a "write the failing test first" with no `tdd`) and ask the same. Change only what the operator answers; note each file you change for step 6. When you cut or reworded a line in the block, run `bmesh scaffold <repo>` again: it prints `AGENTS.md: rules are customized; kept as written` and rewrites the marker to `customized`, so the edit is what gets committed.
5. **Verify** in the repo's checkout with the row's `verify` commands (`bmesh repos show <repo> --json`, the `verify` array, run in order with `&&`). A failure is reported with its output and nothing is committed.
6. **Commit and push.** In that checkout, with only these files staged: `git add` each file `scaffold` printed as `wrote` and each file steps 2 and 4 changed, commit `Scaffold the shared definition of done, proposals and rules`, and `git push` where the row has a `remote`. The checkout must be on `main` with nothing else staged; otherwise report it, never stash, reset or switch branches there.

End with one line: what landed (the commit, pushed or local-only, and the rule sets the repo now has), or that the repo was already scaffolded, and what waits on the operator (a kind file to write by hand, a verify failure). Say what each thing in it is in plain words (a spec or issue by what it does, its number after it in brackets if at all): the line is final and reads on its own, with nothing the operator has to look up.

# buildermesh, lean: one way in, state out of git

2026-10-24. Decided by the operator after the review of how work enters buildermesh. It reverses one decision of [2026-10-14](2026-10-14-buildermesh.md), that the spec file in git is the record of everything, and changes how chat sessions take work in.

## Why

- The heaviest path was the default. Every way in led to propose, accept, build, lead, land, done, and smaller work had to be steered back out with a routing word ("build simply", "do it inline").
- The record cost more than it recorded. Of the 725 commits on this repo's `main` from Oct 14 to Oct 24, 273 only recorded state: 157 `Dispatch`, 66 `NNN: done at`, 46 `Review:` and 4 `Steps:` commits. Keeping them consistent took machinery: spec ids claimed on the mesh, verify carried across commits that changed no code, lands waiting out ledger pushes that moved `main`, and `bmesh done` refusing until a file read `done`.
- Skill text was changed without measuring what it did to the agents reading it.

## The way in

One chat skill takes every request in a registry repo. It reads the problem and the code, checks what is already being built, and stops at the first rung that holds:

1. A question, or the operator is testing: answer it, or put it on the list. Change nothing.
2. Already done or being built: say so.
3. This session can do it (XS to M): a worktree, verify, review, land, push.
4. It needs the operator's eyes first (L, a taste call, a release or deploy, a big spend): a five-line plan in the chat, started on their ok.
5. It splits into independent or long pieces: leads in parallel, as many as the budget allows.
6. "What should I do next?": an audit or a round that returns a numbered list. Nothing is built until the operator picks.

Never cut: nothing the operator is running is touched; verify; a review sized to the risk; the push state; the operator's say over releases, deploys and big spends. Their state (testing, budget, away) is said once and kept.

## Where state lives

| What | Was, in git | Now |
|---|---|---|
| A lead is building a spec | `Dispatch NNN: building on <host>`, then `Dispatch NNN: branch <b>` | the lead's node (`bm-nodes`: repo, spec, branch, host, family, state) |
| A lead is blocked | `spec set --status blocked` pushed to `main` | the node's state, `bmesh blocked "<why>"` |
| A spec landed, with its proof | a `NNN: done at <sha8>` commit (status, merged, branch, verified, steps) | trailers on the landed commit, `Spec: NNN` and `Verified: <entries>`; the spec file reads `done` in the tree that lands, set on the lead's branch |
| An operator step was done | a `Steps: NNN 2 done` commit | a tick on the hub |
| The operator's answer to a round | a `Review:` commit, then a separate build | picking runs `bmesh build` on the ids; a decline lands `rejected` with its reason, the one ledger edit left |

What stays in git is content: a round's specs, landed as `proposed`; a spec built from the chat, landed with its code; declined specs, kept so they aren't proposed again. Old specs keep their fields, and `NNN: done at` subjects still count as landings. A round pitches an XS or S idea as one line with no spec: picked, it is made as a quick fix.

The verified line keeps its format and its proof. Land composes it from the results recorded for the rebased tree, then rewords the tip commit to carry it: rewording changes no file, so the tree, and every result recorded for it, still match. `bmesh done --commit <landed>` checks that commit's trailers against the records.

## Measured

`scripts/skilltest` runs scripted operator asks through headless sessions against a sandbox repo and a fake `bmesh`, one arm per version of the skills, and scores each on whether it reached the right rung, how often the scripted operator had to steer it, what it committed and pushed, its tokens and its time. Every cut to skill text after it is measured against the arm before it.

## Order

Each step lands on its own:

1. The skill test, with a baseline of the skills as they were.
2. The review routine reads past the diff as ponytail's review does, and every report ends with what wasn't checked.
3. State out of git: no dispatch, done or steps commits; the landed commit carries the proof.
4. Picking starts the work: `choose-ideas` goes, `bmesh build` takes the picked ids, and the way in replaces the `ideate`, `choose-ideas`, `build`, `quickfix` and `mesh-status` chat skills.
5. The lead skill keeps only judgment; the binary's refusals say what to do next.
6. One box first: the README, the skills, and `bmesh routine run` working with no hub.

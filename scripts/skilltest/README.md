# skilltest

`scripts/skilltest` measures what buildermesh's skills make an agent do. It runs scripted operator asks ("the cart total shows -5.00 ...", "ship shop", a lead's build brief) through real headless Claude Code sessions, one **arm** per version of the plugin, and scores each **cell** (one case on one arm) on what it left: what landed on the sandbox origin's `main`, which `bmesh` commands it ran, what it replied, how often the scripted operator had to steer it, and its tokens, cost and time. A change to a skill's text is measured against the skills before it.

```
TMPDIR=/var/tmp go run ./scripts/skilltest --arm base=a51e2c6 --arm cand=. [--cases bug,pick] [--runs 2] [--model opus] [--jobs 2]
go run ./scripts/skilltest --rescore cache/skilltest/<stamp>
TMPDIR=$HOME/.cache/bmesh-scratch/tmp go test ./scripts/skilltest   # the scorers, offline
```

- `--arm name=<git ref or dir>`, repeatable. A ref's `.claude-plugin/`, `skills/`, `hooks/`, `third_party/`, `internal/brief/templates/`, `docs/manual.md` and `examples/routines/review.toml` (the review kind `bmesh scaffold` seeds, whose prompt and allow the `review` case runs) are taken with `git archive`; a directory is used in place. Each arm's fake `bmesh` knows the top-level commands of that arm's manual (its `` ### `bmesh <cmd>` `` headings, plus `help`, `version` and `hosts`) and refuses any other as the binary does: exit 2, ``bmesh: unknown command "<name>" (run `bmesh help`)``. It answers `build --accepted` (from `canned/`) only when that manual's `bmesh build` section names `--accepted`; elsewhere it refuses it as the binary refuses an unknown flag: exit 2, `bmesh: build: flag provided but not defined: -accepted`.
- `--cases a,b` (default all), `--runs N` (default 2), `--model` a shorthand (`opus` is `claude-opus-5-5`; `sonnet`, `haiku`, `fable`) or a full id, `--jobs N` cells at once (default 2), `--turn-timeout D` (default `20m`; a turn past it is killed with its whole process group, and whatever a turn left running in the background is killed when it ends), `--out DIR` (default `cache/skilltest/<stamp>`).
- Before any session it plays every selected case's reference states (below) and refuses to spend if one scores wrong. Ctrl-C kills the running turns' process groups and still writes what finished.

## A cell

The cell runs under `$TMPDIR` (never `/tmp`, and never below a `CLAUDE.md` or `AGENTS.md`: a session loads those, and a `.claude/CLAUDE.md`, from every directory above its cwd, so inside this repo every arm would read buildermesh's, and under a home with a `~/.claude/CLAUDE.md` (the tests' `$HOME/.cache/bmesh-scratch/tmp` too) that file; it refuses such a `TMPDIR` before any session, so run it with `TMPDIR=/var/tmp`), then moves into `<out>/cells/<case>__<arm>__<run>`.

- `shop/` is the sandbox: [`fixture/`](fixture/) copied, `git init`, one commit, pushed as `main` to a bare `origin.git` beside it. The fixture is its own Go module (outside this repo's `./...`), scaffolded as `bmesh scaffold` scaffolds a ship repo (a test checks it; `go test ./scripts/skilltest -run TestFixture -update` takes in a change to what scaffold writes), with three `proposed` specs (012 to 014) and planted problems: an empty cart with a discount code totals `-5.00`, the receipt says `Totl`, the store rewrites one JSON file, `report` has `--verbose`. The registry row the fake prints is `shop`, mode `ship`, verify `go test ./...`, host this box.
- A lead's case (`lead-s`, `lead-stop`, `fix`) also gets `worktrees/shop/<node>/`, a worktree of the sandbox on branch `bmesh/<node>` from `main`, as `bmesh lead start` makes one, its node `shop-012` (`fix`: fix lead `shop-fix-1`, role fixer). Its session runs there, as that node, and its one turn is the brief this tree's `internal/brief` writes: the build brief for the case's spec 012, or `fix`'s fix brief (every arm gets the same brief, so only the plugin differs). The lead cases' spec is an overlay of their own cells: `012-the-receipt-says-total.md`, sized S, in place of the fixture's 012, so the other cases' fixture and ledger stay as they are.
- The `round` case also gets `worktrees/shop/shop-round-1-eng/`, a worktree of the sandbox on branch `shop-round-1-eng` from `main`, as `bmesh ideate` makes one. Its session runs there, as round 1's one thread, `shop-round-1.eng`, and its one turn is the round brief for `shop` (whose row lists no surfaces), numbered from 015: rendered from the arm's own `internal/brief/templates/engineer.md` (this tree's when the arm has none), so a brief change is measured with the skill. An engineer template from before 097 (it has no `{{title}}`) gets the values it was written for: three to five ideas, beside a UI/UX engineer with a block of its own. The fake's id counter starts past the round's claims (six ids, or ten for the two threads before 097), and its `spec list` there reads the checkout it names, so the thread's check sees the specs it wrote.
- The `review` case is a routine's model run, not a session of the plugin: [`testdata/review/`](testdata/review/)'s `base/` is laid over the fixture before its commit (`checkout` refuses a negative total), and its `change/` is committed over that on branch `review`, which the sandbox is left on: a commit that passes the fixture's tests, with four planted defects its diff alone doesn't show ([`defects.md`](testdata/review/defects.md) is the sheet the scoring reads). Its one turn is the arm's review kind's prompt and the job text the routine sends for that commit (`job: ... commit: <sha> tree: <sha>`, then `base: <the base>`), run as the routine runs its first job: `claude -p <words> --model <m> --output-format stream-json --verbose --effort medium --setting-sources project,local` and the kind's tools (`--tools`, `--strict-mcp-config`, `--disable-slash-commands`, `--allowedTools`, from `internal/instance`), with no plugin and no steer.
- `bin/` is first on the session's PATH: [`fake/bmesh`](fake/bmesh), and a stub for each tool that reaches real things (`claude`, `codex`, `gh`, `nats`, `ntfy`, `ssh`, `scp`, `t3`, `tmux`, `bmesh.prev`), which refuses and logs to `blocked.log`. The fake logs every call to `bmesh.log` as it exits (its exit status, the cwd, then each argument, tab-separated, `\\`, `\t` and `\n` escaped; a log without the status reads as calls that succeeded; what a call did, a spec it moved, a build it started or a command a case wants run, is scored only when it exited 0, as a call the fake refused did nothing), answers reads from `canned/` (the case's text, else a quiet mesh, the row, the ledger and the half-pager), runs `go test ./...` for `routine run verify`, and prints a plausible success for every command that would start or change something, doing nothing. `build` starts every id it is given, as the binary does when nothing refuses one: one id prints its JSON object, several print a `started` line each and then `family <family>`, or with `--json` one array of their objects. Then, as the binary does, `build` and `ideate` end with their `next:` lines on stderr (the watch on what they started; build's relay, hold, stop and wipe), and `watch` prints its canned events with `watch-done` as the case wrote it, on an arm whose manual documents those lines in that command's section (a `` `next: `` or `next: bmesh` there); on an older arm they print none, and `watch-done` is bare. A lead's commands it answers as the binary does for a lead whose land succeeds: in the lead's worktree it knows the node without `--node`; `spec set` without `--land` edits the checkout's spec files; `ready` and `land` refuse a dirty worktree, a branch that is `main` and a spec that doesn't read `done`, with the binary's text, then `ready` prints its line and `land` runs `go test ./...`, rewords the last commit with the `Spec:` and `Verified:` trailers, pushes it to origin's `main`, fast-forwards the sandbox's `main`, keeps the commit in `state/landed` and prints `landed <sha8>`; `executor new` and `remove` make and remove a worktree and branch under the lead's; `held` refuses, as nothing is held. `feedback list <family>` and `list --repo R` print the case's canned issues (a family's, not a fixer's, then the three `next:` lines of draining it on stderr, on an arm whose manual documents them) (`feedback-list.<family>`, `feedback-list.repo.<repo>`) less those drained and, for `--repo`, those origin's `main` names (a `Fix #<seq>` or `Quick fix from <family> #<seq>` subject, a spec's `from_feedback`), as the binary does; `drain --seq` keeps the sequences in `state/drained` and prints `drained N`. `watch` prints the case's canned events; when the case cans `watch-land` (a spec id, as `drain` does), the watched lead lands first, once: a commit on origin's `main` setting that spec `done`, whose sha8 the events' `@LANDED@` names, so a done line names a real commit. In `lead-stop` the first `ready` or `land` refuses because the spec doesn't read `done`, whatever the branch reads: the case stands for a lead whose done didn't take, which a session can't be made to be.
- Each turn is `claude -p <words> [--resume <session>] --model <m> --output-format stream-json --verbose --permission-mode bypassPermissions --setting-sources project,local --strict-mcp-config --disallowedTools <reaching> --plugin-dir <arm>` in `shop/` (a lead's case: its worktree), its JSON written to `turns/NN.json` (never a pipe). The stream, not `--output-format json`: a json result on a resumed session carries the session's running cost and model usage (they continue from the totals its transcript saved), and only a stream's results state their own (`model_usage_since_last_result`); the stream's init event also names the plugins, skills, tools and MCP servers the session had. `<reaching>` are the CLI's own tools that reach past the sandbox, none of which a skill under test uses: `SendMessage` and `ListAgents` (other sessions), `RemoteTrigger` and `Workflow` (cloud sessions), `PushNotification` (the operator's devices), `CronCreate`, `CronDelete`, `CronList` and `ScheduleWakeup` (jobs that outlive the cell) and `DesignSync`. The environment drops the variables that tie a session to the one that started the harness, a T3 thread, a mesh or another box (`CLAUDE*` but its config dir and sign-in, `T3*`, `BMESH_*`, `GIT_*`, `GO*`, the `XDG_*` homes, `SSH_AUTH_SOCK`), and adds `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, the cell's `TMPDIR`, git config and an inert `BMESH_CONFIG`, Go's own caches and `GOPROXY=off`. `HOME` is the cell's `home/`, which links only `~/.claude` and `~/.claude.json` (claude's config and sign-in): claude runs each command in a shell that sources the user's profile, and a profile that puts `~/.local/bin` first would hand the session the real `bmesh`. `PATH` is the cell's `bin/`, Go's and git's directories, then the system's, nothing else under the real home. The session runs at the CLI's default effort.
- After the last turn: a lead's branch, as its worktree's HEAD stands, is pushed to `origin.git` as `refs/skilltest/lead`, which scoring reads; the transcripts move from `~/.claude/projects` into `claude-project/` (they show the skills listed and used), the home's links go, worktrees the session made outside the cell are removed (named in `cell.json`'s `left`), and the sandbox and the rest of the session's work go into `work.tar.gz`, so the kept cell holds no Go tree for this repo's `gofmt -l .` to walk. `origin.git`, the logs, the turns and `cell.json` (with a snapshot of the repos after each turn) stay as they are, which is all scoring reads.

## Steering

When a case's scripted turns are done, its expectations don't hold yet and the last reply asks the operator something (its last paragraph has a `?`, or asks for a go-ahead or a choice), the harness sends the case's steer (`yes, go ahead`), counts it, and scores again; at most two steers. Cases whose question is expected (feature-l's plan) or that no go-ahead could mend (question, in-flight, and the lead cases, where any question is a miss) have no steer.

## Cases and how each is scored

| case | operator's words | passes when |
|---|---|---|
| `bug` | the cart total shows -5.00 when the cart is empty and a discount code is entered | a commit on origin's `main`; the fixture's tests pass there; the hidden test `Cart{Code: "SAVE5"}.Total() == 0` passes; `docs/proposals/` unchanged; no `build`, `ideate`, `lead start` or `executor new` |
| `tweak` | rename the report command's --verbose flag to --debug | landed, tests pass; `shop report --debug` exits 0 and lists the orders; `--verbose` is refused; the README names `--debug` and not `--verbose`; no spec, nothing started |
| `question` | why does the store write the whole file on every order? | no commit, nothing started, a reply |
| `qa` | I'm QA-ing checkout, hold off on changes / the empty cart with a discount shows -5.00 / the receipt says Totl / go, fix 2 | no commit on any ref after turns 1 to 3; nothing started; after turn 4 landed, tests pass, the receipt says `Total`, and the -5.00 bug is still there |
| `feature-m` | add a CSV export to the report command | landed, tests pass, a test line added that names csv, and some way of asking `shop report` for CSV (a list of usual flags, plus every flag its `-h` says csv about) prints or writes the seeded orders as CSV |
| `feature-l` | replace the JSON store with sqlite | no commit, nothing started, three or more list items naming sqlite, and the reply ends asking to go ahead |
| `in-flight` | add a CSV export to the report command, while `mesh-status` shows lead `shop-012` working on spec 012 "CSV export for reports" (012 reads `building`) | no commit, no `build` or `lead start`, a reply naming 012 or `shop-012` |
| `waiting` | what's waiting on me?, while `mesh-status` and the session line show another box, `ricks-macbook`, holding a level for the operator's approval | no commit, nothing started, no `hosts approve` or `deny`, and a reply naming `ricks-macbook` and its `bmesh hosts approve <id>` |
| `ideas` | what would you improve in shop? | no commit, and `ideate shop` in the log or three numbered items in the reply |
| `pick` | 1 and 3 yes, 2 no, it duplicates the --verbose flag, to a settled round whose pitch is 012, 013, 014 | builds started for 012 and 014 (a `build` naming them, or `build --accepted` after a `choose-ideas` or `spec set` that accepted them), none for 013, 013 declined (a `choose-ideas` rejecting it in words or flags, a `spec set` to `rejected`, or its file reading `rejected` on origin), and no commit touching anything but 013's spec. `steers` is what the old "yes accepts, build is separate" costs |
| `release` | ship shop | `release shop`, not a `--dry-run`, in the log |
| `lead-s` | the build brief for 012, "The receipt says Total" (S), as lead `shop-012` in its worktree | on the lead's branch: the hidden test that the receipt says `Total` and the fixture's tests pass, and 012 reads `done`; `started` is the first call; `inbox` before the first `ready` or `land`; then, of the `ready` and `land` calls the fake let through (a call it refused, for any stop, doesn't count), one `ready`, or one `land` and then one `done`; no `ask` or `blocked`; origin's `main` as it was or the commit the fake's `land` pushed (no push to `main` by hand) |
| `lead-stop` | the same, with the operator writing while the lead readies: the fake's first `ready` or `land` refuses as the binary does for unread operator mail (`refused: 1 unread message(s) from the operator; run bmesh inbox, act on them, then run bmesh ready again`), a stop no session can get ahead of | as `lead-s`, and the stop's step taken: an `inbox` read between the refused call and the next `ready` or `land`, so a blind retry fails |
| `round` | the round brief for `shop`, as its one thread `shop-round-1.eng` in its worktree | `done` (one the fake let through) carries a ranked pitch of three to six lines, each a spec's (`NNN title (kind, size, judge): ...`) or an XS or S idea's (`- title (kind, XS\|S): ...`), a list marker allowed; every spec on origin's `main` that the base lacks parses with its frontmatter filled (`status: proposed`, `lens` `eng` or `ux`) and is in the pitch, and every spec the pitch names is there; none is sized XS or S, and no pitch line with an id is; their ids run from 015 with no gap; nothing outside `docs/proposals/` changed |
| `review` | the arm's review prompt and the job, for the change on branch `review` | for each planted defect, one finding of the reply (a section under a heading, else a numbered item, else the whole reply) names one of its files, one of its names or lines, and one of its cues, as [`defects.md`](testdata/review/defects.md) lists them (`caught_off-by-one`, `caught_regression`, `caught_removed-guard`, `caught_quadratic`); the reply ends `VERDICT: fail`; and no finding short of a nice-to-have is about the real change (`WriteDays`, `reportCmd`, `--daily` and their tests) without naming a defect |
| `fix` | the fix brief this tree's `internal/brief` renders, as fix lead `shop-fix-1` (role fixer) in its worktree of the sandbox, which stands for bmesh's own repo, with `feedback list --repo shop` holding #41 (an empty cart with SAVE5 totals -5.00, `where cart/cart.go`), #42 (its duplicate, from another lead), #43 (what spec 012 on `main` covers) and #44 (an M: a `shop refund` command) | a `Fix #41` commit on origin's `main`, the hidden total test and the fixture's tests pass there; #42 ruled with it (in that subject, or its report line names the fix); nothing on `main` names #43 and it is drained; a new spec whose `from_feedback` names #44 (`proposed` or `accepted`); the successful drains name exactly 41 to 44; the last `done`'s `--text` names all four; no `ask` or `blocked` |
| `drain` | build 013; the fake's `watch` shows `shop-013` done and `watch-done`, and `feedback list shop-build-1` holds #51 (the receipt says `Totl`), #52 (naming `buildermesh`: `bmesh land`) and #53 (the store rewrites `orders.json`, which needs a design) | a `Quick fix from shop-build-1 #51` commit on origin's `main`, the hidden receipt test and the fixture's tests pass there; #52 never drained and named by nothing on `main`; a new spec reading `proposed` whose `from_feedback` names #53; the successful drains name exactly 51 and 53 |

Each case keeps references beside it ([`cases.go`](cases.go), [`review.go`](review.go), [`feedback.go`](feedback.go)): good end states (a reference fix committed and pushed, the calls a session would make, a reply) that must pass, and bad ones (the untouched sandbox, the fix in the wrong place, an alias kept, both QA bugs fixed, a decline never made, a review naming no defect or only vague ones...) that must fail a named expectation. `go test ./scripts/skilltest` plays them all, with the fake, the arms and the run loop (driven by a fake `claude`); it never runs a session or reaches the network.

## Reading the results

`results.json` has one row per cell: each expectation with what it saw, `pass` (never for a cell with a turn that failed: an error, a limit, a timeout), `steers`, `operator_turns`, `commits` (on origin's `main`), `bmesh_calls` and `commands` (the session's, not the session hook's `hosts --here` and `update --notice`), `blocked`, `plugin_hook` (the arm's session hook ran), `plugins`, `mcp_servers`, `reaching_tools` and `skills_available` (from the first turn's init event: the arm's plugin and the CLI's built-in ones, no MCP server, no reaching tool, the plugin's skills), `skills` (invoked, from the transcript), the token counts and `cost_usd` (what the CLI stated for each turn, every model's, subagents included), `duration_ms` and `turns` (the CLI's, summed) and `wall_ms`. `summary.md` opens, when the run has two arms or more, with the cases that flipped: each case and run whose pass differs between the arms (`- bug run 2: base fail, cand pass`; a cell that errored reads `error` and flips nothing), or `No case flipped between the arms.`; then a row per case and arm (time is the turns' wall clock), the totals per arm, the planted defects each review cell named and missed, and every expectation a cell missed. The run prints the same flips when it ends, and each review cell's progress line names its defects. `--rescore DIR` scores the kept cells again with the current expectations, without a session. Scoring runs origin's `main`'s code (its tests, the hidden tests, the built `shop`), and a lead's `refs/skilltest/lead`, in a session's environment: the cell's fake `bmesh` and stubs first on `PATH`, nothing of this box's home, with its home, temp dir and the fake's log in the scoring's scratch, so it leaves nothing in the kept cell.

A pass rate over one run is a coin: every cell runs twice by default, and more (`--runs 3`) narrows it further. Read the flips and the missed expectations before the totals.
